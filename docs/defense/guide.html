1. The story in 60 seconds

The problem. Lea is a student. Her exam is in two days. She has a 24-page PDF of course notes and nine questions. She does not want to re-read everything, and a normal chatbot has never read her notes: it would happily invent an answer. Also, her notes are private.

What Sensai does. You give it a PDF and a list of questions. For each question it finds the right passages in the PDF, asks a small AI model to answer using only those passages, and writes the result into a file answers.md: the answer, the page, and a word-for-word quote you can check. It then double-checks itself in two ways. Everything runs on the laptop: no internet, no cost, no data leaving the machine.

Say it (30 seconds)

"Sensai is a local assistant that answers questions about a PDF and always shows its source: the page and an exact quote. It runs fully on the laptop with a small open model through Ollama. We do not use any AI framework: we wrote every step ourselves. Each answer is checked twice: a plain-code check that the quote really exists, and a second model call that judges the answer. When the two disagree, the tool flags it for a human."

My part (Pacôme)

The project was split in two halves. Mine is the "plumbing": everything that gets the PDF ready, writes the result, and lets a person use it.

2. Words you must know, from zero

Read these once. Whenever a later section uses a word you forget, come back here.

Model (LLM)

A program that predicts the next piece of text. You give it text, it writes text back. Ours is qwen3:4b ("4 billion parameters"): small, about 2.5 GB, runs on a laptop.

Ollama

A free program that runs models on your own computer and offers them through a local web address (http://localhost:11434). Our code talks to it like a phone call: send a request, get an answer.

Token

A piece of text the model reads, roughly 3 or 4 characters. Models count in tokens, not words.

Context window

The maximum amount of text (in tokens) the model can look at at once: question + passages + answer. Ours is 4096 tokens (about 3,000 words). A 24-page PDF does not fit, which is why we only send the best passages.

Prompt

The text we send to the model: instructions + passages + question. The prompts live in prompts/*.txt so they can change without touching code.

Embedding / vector

A text turned into a list of numbers (768 of them for our model) that stands for its meaning. Similar meanings give similar numbers. "How do plants make food?" lands near "photosynthesis" even with no shared word.

Cosine similarity

A score for how much two vectors point the same way. Near 1 = same meaning, near 0 = unrelated. We keep the best 4 chunks.

RAG

Retrieval-Augmented Generation: first retrieve the relevant passages, then generate an answer from them. Like an open-book exam where we hand the student only the right pages.

Chunk

A small piece of a page (800 characters). Small pieces match a question more sharply than a whole page, and they fit in the prompt.

Overlap

Consecutive chunks share some characters (150), so a sentence cut at a border is still whole in one of them.

Index

The saved file (demo.index.json) holding every chunk with its page and vector. Built once per PDF, like the index at the back of a book.

JSON and schema

JSON is a strict text format for data: {"answer": "128 bits", "page": 13}. A schema says which fields must exist. We force the model to answer in this shape so our code can use it.

Retry

If the model's JSON is broken, ask again (at most twice more). After that the question is reported as failed and the file is not touched.

Quote check

Plain code (no AI) that checks the model's quote really appears in the passages we gave it. Proves the quote exists, not that the answer is right.

Judge

A second model call that reads question + passages + answer and says faithful / partial / unfaithful. Catches misreadings the quote check cannot.

CLI

Command-line interface: you type a command in the terminal. python -m src.cli data/demo.pdf data/questions.txt.

Server, HTTP, SSE

A server is a program waiting for requests. HTTP is the language of the web. SSE (Server-Sent Events) lets the server push updates to the browser one after another over a single request: that is how answers appear live.

Atomic write

Writing a file so it is never half-written: write a temporary copy, then rename it over the real file in one instant.

Upsert

"Update or insert": replace the section if it exists, add it in the right place if not.

3. The system in one picture

Think of a library assistant. ingestion.py reads the book and writes index cards (one per paragraph, with the page). store.py is the card drawer. pipeline.py takes a question, pulls the 4 best cards, reads them, writes an answer. judge.py is a second person who double-checks. writer.py copies the answer onto the right page of a report. ollama_client.py is the phone used to call the "brain". cli.py is the manager who orders everything.

Say it

"There are two phases. Once per PDF we ingest it: read the pages, cut chunks, turn each chunk into a vector, save an index. Then, for each question, we retrieve the four closest chunks, ask the model for a JSON answer, check the quote, ask a judge, and write one section of answers.md. My part is the left side (ingestion), the writer, the CLI that orders everything, and the web interface."

5. Where each object lives and how data moves

A program is just data moving between boxes. These are the five shapes of data in Sensai. If you can draw them, you understand the architecture.

Where files are placed on disk. The index sits next to the PDF: course.pdf becomes course.index.json (ingestion.index_path). The answers file defaults to answers.md next to the PDF (or --output). In the web UI, uploads go to WEB-UI/workspace/uploads/ and answers to WEB-UI/workspace/outputs/. Chat conversations of the web UI live in the browser (localStorage), not on the server. Terminal chat sessions are saved by the memory feature under .sensai/.

How data moves. Only one thing talks to the model: the functions in ollama_client.py (plus the terminal chat, which streams with its own small request). Everything else passes plain Python values around: a list of pages, a list of chunks, a dict for an answer. Nothing is global or hidden; each function receives what it needs and returns a result. That is why 398 tests can check every piece without a model.

6. src/ingestion.py: from PDF to index mine

Job: turn a PDF into small searchable pieces and save them. Four functions, in order: extract_pages → chunk_pages → ingest (which embeds and saves), plus index_path and _load_index helpers.

6.1 extract_pages(pdf_path): read the text, page by page

Returns a list of (page_number, text). Page numbers start at 1. Before reading, it makes a series of safety checks, in this order, each with a clear error message:

  1. The file exists, else IngestionError("PDF not found").
  2. Its first 5 bytes are %PDF-, else "is not a PDF file" (a renamed .txt is rejected).
  3. If it is encrypted and an empty password fails: "password protected".
  4. If the PDF library (pypdf) cannot parse it: "Cannot read ... as a PDF".
  5. If the whole document has fewer than 50 characters of text, it is probably scanned images: NoTextError. We do not do OCR.

A page with no text is kept with an empty string, so the page numbers of the other pages stay correct.

Trap

"What if the PDF is scanned?" We detect it (under 50 characters in total), stop with a clear message, and build no empty index. OCR (reading text from pictures) is out of scope: a known limit, said honestly.

6.2 chunk_pages(pages, size, overlap): cut into pieces

For each page: collapse all whitespace to single spaces, then cut windows of at most size characters, moving forward by step = size − overlap. Rules:

  • A chunk never mixes two pages, so its page number is always exact (that is the whole point of a sourced answer).
  • Consecutive chunks of one page share exactly overlap characters, so a sentence cut at a border is whole in one of them.
  • Empty pages are skipped. Invalid settings raise ValueError (size ≤ 0, negative overlap, or overlap ≥ size, which would loop forever).
step = size - overlap
start = 0
while True:
    chunks.append({"text": text[start:start+size], "page": page})
    if start + size >= len(text):   # this chunk reached the end of the page
        break
    start += step

Real example (the code's own output): the letters A to Z with size 10, overlap 3 give step 7 and 4 chunks: ABCDEFGHIJ, HIJKLMNOPQ, OPQRSTUVWX, VWXYZ. Notice HIJ ends the first and starts the second: that is the overlap. For the demo PDF (24 pages, 34,597 characters) the committed settings (800 / 150) give 59 chunks.

Tool: the chunking playground

This is the same algorithm as chunk_pages, ported to the browser. Change the numbers and watch the chunks. Orange characters are the overlap.

6.3 ingest(pdf_path, config, force, progress): embed and save

  1. Reuse rule: if X.index.json exists, you did not pass --force, and the index is not older than the PDF, load it and skip everything (saves minutes).
  2. Otherwise: extract_pages → chunk_pages with the chunk_size and chunk_overlap from config.json.
  3. Embed in batches of 16 chunks per request to Ollama (one request per chunk would be slow). It checks that the model returned exactly as many vectors as texts.
  4. Build the records {id, text, page, vector} and save them with store.save.
  5. The index is written only after every chunk is embedded: a crash halfway never leaves a half-built index.

progress is an optional callback. The CLI leaves it empty and prints lines; the web UI passes a function that turns each stage (reuse, embedding, saved) into an event for the progress bar. One function, two front ends, no duplication.

_load_index validates a saved index: if the file is unreadable or each record lacks id, text, page, vector, it says "Rebuild it with --force" instead of crashing.

Trap

"You change the chunk size. Does the index update?" No. The reuse rule only looks at file dates, not at settings. After changing chunk_size or chunk_overlap you must rebuild with --force (in the web UI: the "Rebuild the PDF index" checkbox). We documented it and say it in the settings dialog. A better design would store the settings in the index and compare them: say that as "what I would improve".

Say it

"Ingestion has three steps: read each page, cut it into 800-character chunks with 150 characters of overlap, and embed the chunks in batches. A chunk never crosses a page, so the page number in the answer is exact. The index is saved only when everything is embedded, and it is reused as long as it is newer than the PDF."

7. src/writer.py: the answers file mine

Job: own answers.md. After each question, change exactly one section and leave every other byte untouched (feature M4, "a living document"). The model never rewrites the file: our code does, so it can never corrupt it.

7.1 The file format

# Answers

<!-- sensai:section 1 -->
## Q1. How many bits long is an IPv6 address?

**Answer:** 128 bits

**Page:** 13

> An IPv6 address is 128 bits long, which gives about ...

**Quote check:** supported
**Judge:** faithful - the passage states 128 bits
<!-- /sensai:section 1 -->

The HTML comments are invisible when the Markdown is displayed but let the code find a section exactly, with a regular expression SECTION_RE that matches from <!-- sensai:section N --> to the matching <!-- /sensai:section N -->. If the judge and quote check disagree, a line Review needed is added (for a refusal, only when the judge says the passages do answer the question). A refusal has page 0, which is written as -.

7.2 upsert_section(path, index, checked)

  1. _validate: the section number must be a positive integer; the answer must be a dict with question, answer, page, quote, status; if it carries an error, refuse to write (WriterError, file untouched).
  2. Read the file (or start with # Answers).
  3. Three cases: same number exists → replace that block only; a later number exists → insert before it (numeric order); otherwise → append at the end.
  4. _write_atomically: write to a temporary file in the same folder, then os.replace it over the real file. The rename is instant, so a crash or Ctrl+C can never leave a half-written answers.md.

Small detail worth knowing: the temporary file is created with private permissions (0600); _target_mode copies the original file's permissions (or the normal default) so answers.md does not become unreadable for others. That was a real bug found by testing and fixed (commit "keep normal file permissions").

Tool: the writer simulator

A tiny model of upsert_section. Click the buttons and look at which sections change (they flash green) and which stay identical.

Trap

"Why does re-running the same question give an empty diff?" Because the model answers deterministically (temperature 0 and a fixed prompt), so the same input gives the same section. To show M4 in the demo, reword the question, re-run with --only 2, and diff the two files: only section 2 changes.

Say it

"The answers file is a living document. Each section sits between two markers. To update a question we find its markers, replace only that block and write the whole file atomically: temporary file, then rename. So nothing else changes, even by one byte, and the file is never half-written. A failed answer is never written."

8. src/cli.py: the entry point mine

Job: wiring only. It reads the arguments and the settings, ingests the PDF once, loops over the questions, prints a summary. It contains almost no logic of its own: it orders the other modules. A conductor, not a musician.

8.1 The command

python -m src.cli data/demo.pdf data/questions.txt            # batch: all questions
python -m src.cli data/demo.pdf data/questions.txt --only 2     # just question 2
python -m src.cli data/demo.pdf                                  # interactive: type questions
flags: --force  --output FILE  --config FILE  --no-judge  --no-rag  --no-quote-check

8.2 What main() does, in order

  1. parse_args (the standard argparse library) reads the command.
  2. load_config reads config.json and fails clearly if a required key is missing (host, chat_model, embed_model, chunk_size, chunk_overlap, top_k). It fills defaults for the feature flags rag, judge, quote_check, cache.
  3. The three --no-... flags switch those feature flags off for this run.
  4. Checks: PDF exists; --only needs a questions file and must be in range; questions are read (blank lines ignored; an empty file is an error).
  5. ingestion.ingest runs once (section 6.3).
  6. If no questions file: interactive(). Otherwise loop over the selected questions.
  7. For each: answer_question then writer.upsert_section. Print one progress line.
  8. Print the summary from eval_summary and return an exit code.

8.3 answer_question(question, records, config)

This is the glue for one question. With RAG on it calls pipeline.retrieve_and_answer (embed, search, prompt, JSON, quote check). With RAG off it calls the model with no passages (to show the difference). Then, if the pipeline did not already produce a verdict, it calls judge.evaluate. A failing judge never loses the answer: it becomes verdict unknown. Finally it sets disagreement (the rule lives in eval_summary.disagrees):

supported     + unfaithful  -> disagreement
not supported + faithful    -> disagreement   (but NOT for a correct refusal)
refusal       + unfaithful  -> disagreement   (the judge says the passages do answer)
Trap: refusals and the flag (fixed, with a history)

When the model correctly refuses (a question not in the PDF), it gives no quote, so the quote check says "not supported", while the judge says "faithful". In our first runs these two "disagreed" and the correct refusal of "Who invented the World Wide Web?" was flagged Review needed: a false alarm. We fixed it: a refusal has no quote, so "not supported" means nothing for it. Now (eval_summary.is_refusal and disagrees) a refusal is flagged only if the judge says the passages do answer the question, i.e. the model refused wrongly. The run summary also counts refusals apart ("Refused: 1/9") so they no longer lower the quote-check percentage. Old recorded runs in docs/examples still show the old behavior. Honest remaining limit: the file still prints "Quote check: not supported" on a refusal.

8.4 The principle: one failed question never stops the run

Each question is inside try/except. If one fails (model timeout, bad JSON after retries) the CLI prints failed: ..., adds it to a list, and goes to the next. At the end the summary lists Failed: Q3 (...). Ctrl+C is also handled: the answers already written are kept.

Exit codeMeaning
0all questions answered
1an input/setup error, or at least one question failed
130you pressed Ctrl+C (the Unix convention: 128 + signal 2)

8.5 Interactive mode

Without a questions file you get a prompt question>. Each answer is printed (format_answer) and written as a section. next_section_number continues after the sections already in the file, so a second session never overwrites the first. exit, quit or Ctrl+D ends it; Ctrl+C cancels only the current question.

Say it

"The CLI only orders the other modules: read the settings, ingest once, then for each question retrieve, answer, judge, and write one section. It is built to never lose work: a failing question is reported and skipped, the judge failing never drops an answer, Ctrl+C keeps what is written, and the exit code tells a script what happened. Feature flags let you switch the retrieval, the judge or the quote check off from the command line, the config file, or the web UI."

9. src/chat.py: the terminal chatbot mine

Job: the base chatbot (task P1): a loop in the terminal where you talk to the model with streaming output. It is also where the extra features X2 (branching) and M3 (memory) show up.

  • History is sent every turn. The model has no memory: it only knows what we send. So messages (system prompt + every user/assistant turn) is resent with each request. This is also why the context window matters.
  • Streaming. stream_reply sends stream: true and prints each fragment as it arrives, so words appear live. It closes the connection in a finally, which makes Ollama stop generating.
  • Thinking indicator. The qwen3 model "thinks" before answering; we print (thinking...) once, and show only the final content (never the reasoning).
  • Errors in plain words: Ollama not running → "Start it with: ollama serve"; model missing → "ollama pull MODEL"; timeout.
  • Ctrl+C during a reply cancels it, removes the half-finished turn from the history (messages.pop()) so it does not pollute the next turns, and returns to the prompt.
  • Commands: /edit (edit a past message and fork a new branch; the old conversation is archived), Ctrl+C mid-reply (stops the model but keeps what it already wrote, so your next message redirects it), /history, /branches, /switch N, /memory and /recall query (cross-session memory: past sessions are saved to .sensai/ on exit and searched by meaning).
A good story to tell (honest testing)

While testing everything, I found that python src/chat.py, the very command written in the README, crashed with ModuleNotFoundError. It had broken when the memory feature added from src.memory import ..., and our automated tests never noticed because they import the module instead of running it as a script. I wrote a failing test first (it runs the file as a real script from a temporary folder), then fixed it with two lines that add the project folder to sys.path. Lesson: also test the real command, not only the functions.

Trap

"Your docs say only one module talks to Ollama." Be exact: the answering pipeline, the judge and ingestion all go through ollama_client.py. The terminal chat (chat.py) is the original base chatbot and streams with its own small requests call; the web UI uses ollama_client.chat_events. If asked, say that honestly, and that merging them into one client would be a clean-up.

10. WEB-UI/: the web interface mine

Job (feature X1): a browser front end over the same backend as the CLI. It does not reimplement anything: the server calls cli.answer_question, ingestion.ingest and writer.upsert_section. The browser just shows progress. Zero extra dependency: the server uses only Python's standard library, and the page uses plain JavaScript (no React, no framework).

10.3 How "movement" works: events

A run takes minutes, so the answer cannot come back in one piece. The server answers /api/run with Server-Sent Events: it keeps the connection open and pushes small messages. The browser (streamPost in app.js) reads them and updates the screen:

EventSent whenWhat the page does
startthe job beginsshows the status line and the progress bar
ingestembedding progress (reuse / embedding done/total / saved)moves the bar: "Reading the PDF: 32 of 59 chunks"
question_starta question beginsshows a shimmering skeleton for that question
question_donean answer is readydraws the answer card: answer, page button, quote, two badges
question_faileda question faileddraws an error card with a retry
summary, donethe endshows the totals tiles; stops the timer
erroringestion failedshows the message, marks the pending questions

Stop button: it aborts the browser request. The server notices the broken connection (BrokenPipeError) and abandons the job; answers already written stay in the file.

10.4 One job at a time

A small laptop cannot run two models at once, so stream_job takes a lock (threading.Lock). A second run or chat while one is active gets HTTP 409 "Another run or chat is in progress". Nothing is lost: the page shows the message.

10.5 Security (a favorite jury topic)

The server has no login, so by default it only listens on 127.0.0.1 (your own machine). On top of that:

ProtectionAgainst what
Host check (check_origin): only localhost, 127.0.0.1, ::1 (+ names you allow) → else 403DNS rebinding: a hostile website pointing its name at your machine
Origin check on posts: a request from another website → 403CSRF: another tab making your browser call your local server
No raw paths. A document is referred to as builtin/demo.pdf or upload/x.pdf; the name must match ^[A-Za-z0-9._ -]{1,120}$ and end in .pdf; the file is found by listing the folder, never by joining user text into a pathPath traversal (../../etc/passwd)
Size limits: upload 50 MB (413), JSON body 1 MB, 100 questions, 1,000 characters eachmemory exhaustion
Settings whitelist (EDITABLE): only listed keys, with min/max; the Ollama host cannot be changed from the UIpointing the server at another machine
Upload validation: the file is tested with extract_pages before it is keptscans, non-PDFs, broken files
Sharing key (--key): a secret in the link; the server sets an HttpOnly; SameSite=Strict cookie; compared with hmac.compare_digest; wrong or missing → 401strangers who find a shared link

Sharing a running page with a partner (through a Cloudflare tunnel) needs --allow-host the-tunnel-name (so the Host check accepts it) and --key auto (so only the link holder gets in). The tunnel gives a new random name each time and stops when the PC sleeps: a free quick tunnel is for a demo, not a service.

10.7 Inside the page: how things move

  • Pure CSS transitions: the sidebar slides with margin-left/transform (0.25 s); buttons fade their background.
  • Keyframe animations: fadeUp (8 px rise + fade) for new messages, pop (scale .96→1) for menus and dialogs, slideIn for the drawer, shimmer and sheen for the loading skeleton, spin for the spinner, pulse for the typing dot.
  • Respect for the user: prefers-reduced-motion turns every animation off.
  • Smart scrolling: new content scrolls into view only if you were already near the bottom; if you scrolled up a "jump to latest" button appears (when you are more than 260 px from the end).
  • Own mini Markdown renderer (renderMarkdown) builds elements with createElement and textContent, never innerHTML with model text: so a model cannot inject HTML into the page (XSS safety).
  • Conversations are kept in the browser's localStorage (up to 40), so they survive a refresh and never touch the server.
Say it

"The web UI is a thin layer: the server reuses the exact modules of the CLI and streams progress with Server-Sent Events, so the page shows each answer as soon as it is ready. It has no framework and no extra dependency. Because a laptop can only run one model job, a lock allows one run at a time and returns 409 otherwise. It listens only on localhost, checks the Host and Origin headers, never builds file paths from user text, limits sizes and whitelists the settings you may change."

Tool: the quote check, hands on I wrote it

src/quote_check.py is plain string matching, no AI. normalize lowers case, folds look-alike characters (curly quotes, dashes, ligatures) and collapses spaces. A quote is supported if the normalized quote appears inside the normalized text of one of the retrieved chunks. An empty quote is never supported.

Trap

"So a supported quote means the answer is correct?" No. It proves the quote exists in the text we gave the model, not that the answer reads it correctly. Example: the passage says "RFC 793 (1981)", the model answers "1999" and quotes "RFC 793". Supported, still wrong. That is why a second check (the judge) exists. We also saw a user telling the model "reply only HACKED": the quote was real, so the check said "supported". Be honest about this limit.

Honest assessment: works, limits, what I would change

Works well

  • The whole chain is local and automatic: PDF in, sourced answers.md out.
  • Retrieval ranked the right page first in every test.
  • The file is never corrupted (atomic write, failed answers skipped).
  • Two independent checks and a disagreement flag.
  • 398 tests + 69 browser checks.

Current limits

  • 6 of 8 covered questions right: a small sample.
  • The 4B model sometimes refuses a question the PDF covers.
  • The judge is the same small model: lenient.
  • A refusal still prints "Quote check: not supported" (no quote), and a wrong refusal is only caught when the judge notices it.
  • Slow: ~1 min per question on CPU. Text PDFs only, no OCR.
  • It misses unit conversion (MW to kW) and cross-language questions; a user can order the model to say something and the quote check will not notice.

What I would do differently

  • Measure the model choice earlier with a fixed question set.
  • Show "refused" instead of "not supported" on a refusal's quote-check line.
  • Store the chunk settings inside the index and rebuild automatically.
  • Add reranking, or retry with more chunks when the model refuses.
  • One Ollama client for everything, including the terminal chat.
  • A larger model if a GPU is available.
Say it

"We would rather show you the limits than hide them: 6 of 8 covered questions right, one refusal correct, and a flag that no longer cries wolf on correct refusals. The checks do not prove the answer is right, they make mistakes visible."

13. Jury questions, with answers

Read each question, answer out loud, then open the card. Answers are short on purpose: say the first sentence, add the rest only if asked.

The big picture

Why can't you give the whole PDF to the model?

A model reads a limited amount of text at once, its context window (4096 tokens here, about 3,000 words). The demo PDF is about 5,500 words, so it does not fit. A bigger window needs more RAM and is slower, and small models get worse at finding details in long text. So we search first and send only the best 4 chunks: that is RAG.

What is an embedding and why does it find passages with different words?

A list of 768 numbers that stands for the meaning of a text. Similar meanings give similar numbers, so "how do plants make food" lands near "photosynthesis turns light into sugar" with no common word, where Ctrl+F finds nothing. Questions and chunks are embedded with the same model so they can be compared.

What is cosine similarity?

A score for how much two vectors point the same way: near 1 very similar, near 0 unrelated. Question [1, 0] against chunk A [0.9, 0.1] scores about 0.99 and against chunk B [0, 1] scores 0, so A wins. Real vectors have 768 numbers but the idea is identical. We keep the 4 best.

Why local, and why no LangChain?

Local: the document stays on the machine, no cost per question, works offline: important for private notes or contracts. The trade-off is a weaker, slower model, which we compensate with retrieval and two checks. No LangChain: the subject asks for no LLM framework in the bot, and writing each step ourselves keeps everything visible and explainable: about 600 lines of plain Python.

My part

Walk me through what happens when I run the CLI.

It reads the arguments and config.json, ingests the PDF once (read pages, cut chunks, embed, save the index, or reuse it if it is newer than the PDF), then for each question it retrieves the 4 best chunks, asks the model for a JSON answer, checks the quote, asks the judge, writes that question's section atomically, prints a progress line, and at the end prints a summary and returns an exit code.

Why chunks, and why overlap?

A whole page mixes topics, so its embedding is vague and it wastes the context window. Small chunks (800 characters) match sharper. A sentence can be cut exactly at a border, so consecutive chunks share 150 characters and the sentence is whole in one of them. Too small loses context, too big blurs the match: both sizes are settings.

Why do you keep the page number in each chunk?

It is free (we know the page when we read it) and it is the whole point of a sourced answer: the user can open the PDF at that page. That is why a chunk never crosses a page.

What if two different PDFs? / What if I change the PDF?

The index is named after the PDF and sits next to it. If the PDF is newer than its index, the index is rebuilt; otherwise it is reused. We handle one PDF at a time: a known limit.

How do you make sure answers.md is never corrupted?

Two things. We never let the model touch the file: our code finds the section by its markers and replaces only that block. And we write atomically: a temporary file in the same folder, then os.replace, which is instant. A failed answer raises an error before anything is written. The tests compare the file byte for byte before and after.

What happens if the model fails or Ollama stops in the middle of a run?

The failing question is reported ("failed: ...") and skipped, the run continues, and the summary lists it. If Ollama is down the error says "Start it with: ollama serve". Ctrl+C keeps what is already written. The exit code is 1 if any question failed, 130 on Ctrl+C.

Why a JSON file for the index and not a vector database?

A few hundred chunks: a database adds setup for no benefit, and a JSON file is readable and easy to test. The cosine search over a few hundred 768-number vectors takes milliseconds with numpy. For millions of chunks we would switch.

What is a feature flag, where do you set it?

An on/off switch for a part of the pipeline (rag, judge, quote_check). You set it in config.json under feature_flags, with a command-line flag (--no-judge, --no-rag, --no-quote-check), or with the three switches in the web UI Settings (group Features, for the current server session). Useful to show what each part adds. Be honest: config.json also contains a cache flag, but it is reserved and nothing uses it yet.

Your chat command crashed once. What happened?

(Section 9.) The documented command python src/chat.py had broken when memory was added, because the file could not find the src package when run as a script. The tests imported the module instead of running it, so they missed it. I wrote a failing test that runs it as a real script, then fixed it. Now 398 tests pass.

The web interface

Why no React or other framework?

No build step and no dependency: the server is Python's standard library and the page is plain JavaScript, so it runs offline and is easy to explain. The cost is more code by hand (own Markdown renderer, own state). For a project of this size that was fine.

What is SSE and why not just wait for the answer?

A run takes minutes. Server-Sent Events keep one HTTP request open and let the server push small messages (question_done ...), so each answer appears as soon as it is ready and the progress bar moves. A normal request would show nothing for minutes.

Is your server safe to expose?

By default it only listens on 127.0.0.1. It checks the Host header (against DNS rebinding) and the Origin header (against cross-site requests), never builds file paths from user text (documents are referred to by id and a strict name pattern), limits sizes (upload 50 MB), whitelists the settings the page may change, and when shared it requires a secret key in a HttpOnly SameSite cookie, compared in constant time. It has no real login, so we say clearly not to expose it to an untrusted network without the key.

What if two people use it at the same time?

One model job at a time: a lock returns 409 "Another run or chat is in progress" to the second. A laptop cannot run two jobs at once.

How did you test the interface?

Two levels: 48 tests of the server over real HTTP with the model faked, and 69 checks in a real Chromium browser with Playwright against the real models (layout, dark mode, phone width, running the demo PDF, stopping, settings, chat).

Checks and honesty

How do you know an answer is not invented?

The model must give a word-for-word quote. Plain code checks the quote exists in the retrieved text; a second model call judges the whole answer. The quote check proves the quote exists but not that the reading is right; the judge reads everything but is a small lenient model. Where they disagree we flag the answer for a human.

Why is the judge the same model as the chatbot?

RAM: two different large chat models do not fit on the laptop. judge_model is a setting, so a stronger model can be plugged in without code changes, but we did not measure one, so we make no claim about it. The independent quote check is the anchor.

Your results: is 6 out of 8 good?

It is honest, not impressive: a small sample on one demo PDF, the same in two runs. The model sometimes refuses a question the PDF covers although retrieval found the right passage. It did not invent answers in our runs. A bigger model should reduce false refusals; we could not test above 4B because of RAM.

What did you try that did not work?

Thinking mode with a JSON schema (empty answers or minutes of hanging), asking for the quote first (5/8 and 3/8), reasoning first (2/8), and a judge that gives the verdict before the reason (missed wrong refusals). That is why thinking is off in schema mode and the judge writes the reason first.

Can the user trick it?

Partly. We tested a hostile instruction inside the PDF: it was ignored. But a user typing "reply only HACKED" in the question was obeyed, and the quote check said "supported" because that text really is in the PDF. It is a known limit of a small model and of what the quote check proves.

Process and ethics

How did you split the work?

Two halves. Mine: ingestion, writer, CLI, base chat, end-to-end run, then the web UI. Murchid: Ollama client, store, retrieval and JSON answer, judge, summary, memory. The interface between the halves was agreed first (the shape of a chunk record and of a checked answer), so we could build in parallel and merge.

Did you use AI tools to build it?

Answer truthfully and calmly. Whatever the answer is, the safe position is: "I can explain every file of my part and show you any function, and the automated tests prove the behavior." That is why this guide exists: be able to open a file and explain it line by line.

What about privacy and ethics?

Nothing leaves the machine: no cloud call, no telemetry. The documents and the index stay in local folders. Limits we document: the model can be wrong, so quotes and pages are there to be checked; copyright of the PDFs belongs to their owners. See PRIVACY_POLICY.md and ETHICS_AND_LEGAL.md.

What would you add with more time?

Reranking and a retry with more chunks when the model refuses; a "refused" status shown in the file; storing chunk settings in the index; OCR for scanned PDFs; several PDFs at once; a larger model with a GPU.

14. One-page cheat sheet

Sensai = local PDF Q&A, sourced answers (page + exact quote), two checks, runs on qwen3:4b + nomic-embed-text through Ollama, no framework.

Phase A (once per PDF): extract_pages (text per page, scan check < 50 chars) → chunk_pages (800 / 150, never crosses a page) → embed (batches of 16, 768 numbers) → demo.index.json (only saved when complete; reused if newer than the PDF; --force after changing chunk settings).

Phase B (per question): embed question → cosine top 4 → prompt with passages → JSON {answer, page, quote} (think off, temperature 0, 2 retries) → quote check → judge (reason first) → upsert_section (markers, atomic) → summary + exit code (0 / 1 / 130).

Writer: sections between <!-- sensai:section N --> markers; replace / insert in order / append; temp file + os.replace; failed answer never written.
