# End-to-end results (task P7)

First full run of the real chain: PDF -> ingestion -> retrieval -> JSON answer -> quote check -> judge -> `answers.md`, with the real Ollama models on the project machine.

> **Important:** the demo PDF from task D1 was not available when this was run. These numbers come from a **stand-in PDF** generated by `scripts/make_demo_data.py` (24 pages about networking, 8 facts planted on known pages, one question the PDF does not cover). **Re-run on the real demo data and replace the numbers below** before the keynote.

## Setup

| | |
|---|---|
| Chat model and judge | `qwen3:4b` (schema mode, thinking off, temperature 0) |
| Embedding model | `nomic-embed-text` |
| Chunking | size 800, overlap 150, top-k 4 |
| Machine | WSL2, CPU only, 7.6 GiB RAM total (about 1.5 GiB free during the run) |
| Data | stand-in PDF, 24 pages, 24 chunks; 9 questions (8 covered, 1 not covered) |

## How to reproduce

```bash
python scripts/make_demo_data.py data/synthetic            # stand-in demo.pdf, questions.txt, expected_answers.md
python -m src.cli data/synthetic/demo.pdf data/synthetic/questions.txt
python scripts/e2e_check.py data/synthetic/answers.md data/synthetic/expected_answers.md
```
`e2e_check.py` exits 0 when at least 70 % of the covered questions cite the right page and every uncovered question is refused. The expected file format is `number | page P | key phrase` (or `number | none |`).

## What we found (and what it means for the keynote)

1. **Thinking vs JSON schema.** `qwen3:4b` with default thinking plus a JSON schema stalled: the first attempt ran 9 min 40 s without finishing question 1. With `think=false` plus the schema, 9 questions took under 4 minutes. In plain chat the opposite holds (without a schema, `think=false` leaks the reasoning into the text).
2. **Prompt design matters a lot in that mode.** A terse system prompt made the model refuse every question. An explicit prompt ("if a passage contains the answer, give it, its page and a word-for-word quote; only if no passage has it, say the document does not cover this") fixed that.
3. **Extraction tricks did not help.** Putting `quote` first in the schema (to force the model to find the sentence first) scored 5/8 and 3/8 on the same questions versus 7/8 for the current order, so we kept the current schema. A separate yes/no "is it answerable" question scored 2/5.
4. **The model misses facts buried in longer passages.** Q3 and Q4 are in the retrieved passages (retrieval ranked the right page first) but the non-thinking 4B model answered "the document does not cover this". This is the main quality limit of the system.
5. **The judge is unreliable on refusals.** With the rule "if the answer is a refusal, check whether a passage contains the answer", the correct refusal (Q9) is judged faithful, but the judge also called the wrong refusals (Q3, Q4) faithful, and for Q3 its own reason sentence contradicts its verdict. Without the rule, the correct refusal was judged unfaithful. A 4B model cannot reliably decide "is the answer in these passages?".
6. **The disagreement flag still pays off.** A wrong refusal shows `not supported` from the quote check while the judge says `faithful`, so it is flagged for manual review. Cost: a correct refusal is flagged too (Q9).
7. **The two checks complement each other.** The quote check is exact but only proves a quote exists; the judge reads the whole answer but is lenient. Together they catch more than either alone.

## Limits to state in the keynote

- 6 of 8 covered questions answered correctly on the stand-in PDF (75 %). The same questions gave 7/8 in a separate harness run, so results vary by about one question between runs.
- The model refuses when it should answer (false refusals); it did not invent answers in this run.
- A correct refusal shows `not supported` from the quote check (there is no quote), which looks like a failure. A dedicated status for refusals would be clearer.
- The judge is the same small model that wrote the answers and is lenient on refusals.
- 26 s per question on CPU; a live demo of 6 to 8 questions takes 3 to 4 minutes, so record a fallback video.
